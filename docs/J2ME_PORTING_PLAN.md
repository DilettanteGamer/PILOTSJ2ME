# План переноса «Братьев Пилотов» на J2ME

Актуальная сборка — [0.23.1: безопасные остановки и удары мышей](SEWER_SAFE_STOPS_0.23.1.md).
Подвал адаптирован для кнопок: фронтальный вид, автоматические прыжки, безопасная дорожка и возврат за автоматом.
Перенесён полный маршрут от ворот до финальной лесной поляны. По новому
решению пользователя канализация возвращена как мини-игра за одного Коллегу:
обрезанный мост, мыши, управление 4/6, автоматический повтор после падения,
без инвентаря. Переход улица → канализация → гостиница работает.

Текущий маршрут: ворота → двор зоопарка → звериный двор → сад → улица →
канализация → гостиница (вступление и интерьер) → комната с балконом →
карниз → ванная → электрощитовая → подвал → крыша → полёт → финальная поляна.
Внутренние сцены: 02 → 03 → 04 → 05 → 06 → 07 → 08 → 09 → 10 → 11 → 12 →
13 → 15 → 14 → 16 → 17. В списке проверки — только 16 анимаций канализации;
игровые ресурсы остальных сцен сохранены.

Сохранены отдельные экраны холодильника 3×3, электрощитка и ящиков подвала,
управление шаром вверх/вниз и исправленные маршруты финала. Поляна завершается
исходной сценой со слоном. Раздельные профили 128×128, 128×160 и 240×320,
сохранения и управление звуком продолжают работать. Последние изменения:
[0.22.3: курсор у веток](FINAL_CURSOR_0.22.3.md),
[0.22.1: совместный прыжок](FINAL_ROUTING_0.22.1.md),
[0.22.0: финал](FINAL_FOREST_0.22.0.md).

Ниже сохранена история ресурсных этапов и исходного плана исследования.

Последняя ресурсная сборка — [0.3.6](ANIMATION_PLACEMENT_0.3.6.md):
створки совмещены с проёмом по исходным ресурсам окна; привязки у ворот сохранены.

Обновление после составления плана: в ресурсной сборке 0.3.4 откалиброваны
позиции 15 анимаций и двух актёров. [Подробности и ограничения](ANIMATION_PLACEMENT.md).
Семь реакций отложены до игровых механик по уточнению пользователя.
Ниже сохранён исходный срез исследования 0.3.2/0.3.3; значения размеров
и статусов в нём относятся к этому срезу, не к новой 0.3.4.

Дата исследования: 21 октября 2026 года. Состояние: анализ прототипа и план
работ, а не объявление о готовности полной игры.

## 1. Основной вывод и цель

Предоставленные JAR — работающий по сообщениям пользователя графический
прототип: просмотр фонов, анимаций и управление курсором. Статический анализ
подтверждает наличие этих механизмов, но не подтверждает повторное выполнение
пользовательских тестов на этой машине. Полная игровая логика пока не перенесена:
во всех 19 файлах `.hot` число областей взаимодействия равно нулю, а встроенная
`ScriptVM` содержит небольшой собственный набор команд, связь которого
с интерпретатором оригинала не установлена.

Ближайшая цель — восстановить воспроизводимую компиляцию движка, извлечение
исходных данных и одну законченную игровую сцену, прежде чем расширять порт.
Первая сцена для такого среза — ID 02, у зоопарка: только для неё в JAR уже
есть актёры и анимации. Идентификатор 02 не следует путать со вторым пунктом
списка анимаций: это независимые пространства идентификаторов.

Цель полного переноса: пройти оригинальную игру от начала до конца на
выбранных MIDP 2.0 / CLDC 1.1 устройствах с сохранением причин и результатов
действий, взаимодействия персонажей, предметов и переходов между сценами.
Состав обязательных звуков и видеовставок определяется отдельной описью
оригинала; молчаливое удаление этих частей не считается завершённым переносом.

## 2. Основания и границы достоверности

Исследованы:

1. Оригинальные Windows-бинарники из репозитория, их Ghidra-декомпиляция
   из коммита `5071a12a10bbf1739a9c5a07085a13463fc4fcc8`.
2. Два JAR 0.3.2, предоставленные пользователем, и полученные из них
   ресурсные сборки 0.3.3 без изменения байткода.
3. CFR-декомпиляция классов 240x320; классы профиля 128x128 побайтово те же.
4. Константные пулы классов, бинарные каталоги, заголовки и все кадры ресурсов.
   Для `GameState` и `ScriptVM` дополнительно просмотрен вывод `javap -c -p`.

Различаем три вида утверждений: **факт** — проверен в байтах/коде; **гипотеза** —
назначение выведено из поведения псевдокода и требует проверки; **план** —
предлагаемое изменение, которого в текущем движке ещё нет.

Игра и MIDlet в этой среде не запускались. Не измерены FPS, heap на телефоне,
совместимость установки и реальное прохождение. Ghidra-псевдокод не является
компилируемым оригинальным C-проектом. Java после CFR также не является
проверенным исходным проектом: `AnimationClip.paint` содержит невосстановленные
переходы, `GameCanvas.run` — предупреждение о восстановлении обработчиков.

### 4.1. Форматы прототипа

Все числа в ресурсах Java читаются big endian. Это форматы текущего порта,
а не доказанное описание данных Windows-оригинала.

| Magic | Файлы | Поля |
| --- | --- | --- |
| `PLT2` | `catalog.bin` | count u16, затем scene IDs u8 |
| `P8BG` | `.p8`, `.bar` | raster width/height и world width/height u16, RGB-палитра 768 байт, width×height индексов |
| `ANM1` | `.anm` | count u16, duration u16, transparent u8, RGB-палитра; кадры: offset X/Y i16, width/height u16, индексированные пиксели |
| `ACT1` | `.act` | count u8; actor ID u16, X/Y i16 |
| `ANC2` | `.animations` | count u16; ID u16, anchor X/Y i16, focus X/Y u16, Java UTF label |
| `HOT1` | `.hot` | count u8; X/Y/W/H и размер действия u16, байты команды |
| `PSV1` | RMS save | scene/X/Y u16, zoom boolean, 64 int, 32 boolean; всего 299 байт с magic |

### 4.2. Реальные команды текущей ScriptVM

| Opcode | Операнды | Реализация |
| --- | --- | --- |
| 0 | — | END |
| 1 | variable u8, value u16 | Установить int-переменную |
| 2 | variable u8, value u16, skip u8 | Если значение не равно ожидаемому, пропустить байты |
| 3 | scene u8 | Перейти в сцену и завершить выполнение |
| 4 | item u8, present u8 | Изменить boolean инвентаря |
| 5 | message u8 | Вызвать служебный `message` |

Есть проверки длины 1–1024 байта, допустимых операндов и границ переходов,
лимит 256 инструкций. Команд проигрывания/ожидания анимации, перемещения
персонажа, выбора активного героя, ветвления по исходу действия, диалогов
и звука в этом наборе нет. Совпадение номеров с оригинальным форматом
не установлено; нельзя выдавать этот адаптер за интерпретатор оригинала.

## 5. Что удалось понять из Windows-декомпиляции

Ghidra обнаружила 341 функцию в `PILOTS.EXE`: 327 декомпилированы,
14 классифицированы как thunks. В `GMW.DLL` две функции не восстановлены;
их дизассемблирование сохранено. Границы обнаруженных функций не гарантируют
полноту покрытия исполняемого кода.

| Адрес / функция | Наблюдаемое в псевдокоде | Практический следующий шаг |
| --- | --- | --- |
| `FUN_00408a04` | Расчёт координат через поля `param_1[4/5]`, масштабные globals, возможную ссылку через поле `+6`, интерполяцию по `[1]/[2]`, флаги 0x08/0x10 и запись X/Y по `+8/+10` | Приоритетный кандидат для исследования привязок/движения; установить структуру, единицы, знаки offset и флаги по трассе оригинала |
| `FUN_0040ba1c` | Прямые вызовы `StretchDIBits` и `BitBlt` | Точка сопоставления графического вывода с `drawRGB`; не переносить GDI API на Java |
| `FUN_0040af64` | Windows-обработка событий и `GetAsyncKeyState` | Сопоставить пользовательские действия и события движка с MIDP вводом |
| `FUN_0040ad04`, `FUN_0040ad7c` | `PeekMessageA`/`GetMessageA`, `DispatchMessageA` | Изучить цикл обработки событий и неблокирующие ожидания |
| `FUN_00409e6c` | `LoadLibraryA`, `GetProcAddress`, строки `UTRegister`, `UTUnRegister`, `GMW_DLL` | Определить роль Win16 thunk-моста; его API-обвязку на J2ME заменять, а не копировать |
| `FUN_0040998c`, `FUN_0040a51c`, `FUN_0040ac08` | Вызовы `midiOutShortMsg`/`mciSendCommandA` | Отправные точки восстановления звуковых событий и форматов |
| `FUN_0040d57c`, `FUN_0040d7d4`, `FUN_0040da70` | `CreateFileA`, `SetFilePointer`, `ReadFile` | Подняться по вызывающим функциям к загрузчикам игровых записей; сами обёртки похожи на файловый runtime |
| `FUN_00405514` | Цикл разбора команд, глобальные токены, вызовы `FUN_00404904`, `FUN_00404980`, `FUN_004048f4`, `FUN_00405150` | Кандидат для изучения сценарного формата; назвать его оригинальной игровой VM можно только после проверки данных и исполнения |
| `FUN_00403a64` | Обработка групп 32-битных записей, флагов, условий и глобальных таблиц | Кандидат для исследования правил/состояния; конкретная игровая семантика пока не доказана |

Наличие большого `switch` само по себе не доказывает наличие игровой VM:
например, `FUN_0040c2a0` копирует перекрывающиеся блоки памяти, а
`FUN_0040c834` содержит разбор форматных спецификаторов. Их нельзя автоматически
считать интерпретаторами сценариев только по сложности псевдокода.

В `PILOTS.EXE` за концом PE-секций по смещению 72704 находятся 48284451 байт.
Это добавленные данные, ещё не разобранные по игровым записям. Полного конвертера
EXE → ресурсы J2ME сейчас нет; уже готовые ресурсы JAR не заменяют такой конвертер.

## 6. Исправление анимаций: отдельный обязательный этап

Замечания пользователя сохранены по исходным номерам меню. Сопоставление
с ID ресурса выполнено по `ANC2`, а не по предположению о номерах файлов.

| Требование | Номер меню → ID ресурса |
| --- | --- |
| Неверное размещение | 02→56, 05→64, 06→66, 09→69, 11→75, 12→76, 13→83, 16→86, 17→87, 18→88, 19→89, 20→90, 23→94, 24→95, 25→97 |
| Привязка к персонажу/результату действия | 14→84, 15→85, 21→92, 22→93, 27→102, 28→103, 30→105 |
| Удалить «Деталь» | 31→106; выполнено в 0.3.3 |

Для остальных пунктов исправлений пока нет. Верные места, персонажи,
правильные/неправильные действия и условия запуска не подтверждены.
Не следует угадывать anchor по центру непрозрачного рисунка: рисунок меняется
между кадрами, а pivot и положение персонажа — часть игрового состояния.

### 6.1. Порядок восстановления

1. Для каждой записи зафиксировать ID, название, стартовый кадр, frame offsets,
   текущие anchor/focus и контекст сцены. Сохранить исходный каталог неизменным.
2. Проследить `FUN_00408a04` и вызывающие функции; установить, что означают
   координаты, ссылка на другой объект, отражение и интерполяция. Сопоставить
   с данными конкретных анимаций 56, 64 и одной привязанной анимации.
3. Получить эталонное поведение из запуска оригинала либо из проверенного
   разбора его структур; картинки с отметками использовать как дополнительный
   источник, не как замену всей модели.
4. Разделить режимы: фиксированный объект сцены; анимация в позиции персонажа;
   анимация перемещения; реакция на действие. Отделить положение камеры от pivot.
5. Предлагаемая модель: `actorId`, world position, facing, pivot,
   `clipId`, состояние действия, frame offset, необязательная траектория.
   Рисовать по контракту `worldPosition + localOffset - pivot`, затем отражение
   и преобразование viewport. Знаки и порядок операций утвердить по оригиналу,
   а не навязать эту формулу формату ANM1 без проверки.
6. Таблица запуска должна хранить условие, исполнителя, цель, исход,
   анимацию, эффект состояния и событие завершения. Внешне одинаковое движение
   при успехе и ошибке не должно автоматически давать одинаковый результат.
7. Предпросмотр оставить отдельным режимом: его тестовая anchor не задаёт
   положение героя в игровом сценарии. Возврат не должен менять инвентарь,
   позицию героя, задачу или сюжетные флаги.

Готовность этапа: все перечисленные пункты имеют подтверждённые привязки,
анимация корректна у границ экрана и при zoom на обоих профилях, а семь
реакций запускаются нужным героем при подтверждённых условиях. Наличие клипа
в меню само по себе этот этап не закрывает.

## 7. Целевая архитектура порта

Разделить настольный конвертер и телефонный runtime. Конвертер выполняет
дорогой разбор, декодирование и масштабирование заранее; телефон читает
компактные проверенные пакеты и воспроизводит игровое состояние.

| Компонент | Предлагаемая ответственность |
| --- | --- |
| Desktop extractor | Неизменяемый оригинал → таблица записей с offset/size/hash/type; декодирование с проверкой границ |
| Intermediate representation | Стабильные scene/actor/item/clip/action IDs, исходные ссылки и источник каждого восстановленного поля |
| Asset compiler | Профильные фоны, палитры, кадры, маски/области, текст и звук; отчёт размеров, детерминированные ресурсы |
| Scene runtime | Состав сцены, фон, панели, порядок отрисовки, интерактивные области и входные/выходные условия |
| Actor runtime | Позиция героя, направление, состояние/траектория, pivot и проигрыватель клипов |
| Action scheduler | Последовательности: подойти → проиграть → дождаться события → изменить состояние → продолжить |
| Logic adapter / VM | Проверенные команды оригинала либо документированная эквивалентная IR; неизвестные команды явно отклоняются |
| UI | Выбор героя, инвентарь, диалог, действие, доступность управления; debug-перелистывание отделено от игры |
| Audio service | Необязательный для работы базовой логики MMAPI-бэкенд, ограничение одновременных players, pause/resume/close |
| Save service | Версионированное устойчивое состояние с проверкой целостности и миграцией |

На CLDC использовать целочисленную арифметику и обычные классы; не вводить
зависимость от Java SE Collections/NIO/desktop API. Поле `Pilots-Screen`
сейчас только metadata: canvas использует фактический размер экрана.
Ресурсный профиль выбирать при сборке и проверять совместно с геометрией.

## 8. Последовательность работ и критерии приёмки

### Этап 0 — зафиксировать базу и отделить режимы (P0)

Сохранить JAR, checksum, меню, каталоги и замечания; отделить исходную 0.3.2
от ресурсной 0.3.3. Составить журнал проверок на реальных целях: модель/эмулятор,
JAR checksum, разрешение, heap, ввод, результат. В репозитории эта фиксация
уже начата: артефакты, опись и статические проверки добавлены данным изменением.
Остаются запуск и протоколы функциональных проверок.

Выход: оба профиля запускаются на выбранных целях; меню, курсор, сцены,
предпросмотр и удаление «Детали» проверены заново, результаты записаны.

### Этап 1 — восстановить компиляцию движка (P0)

Создать отдельный `src/` после восстановления CFR-кода. Устранить
невосстановленный `AnimationClip.paint`; `GameCanvas.run`, синтетические классы,
finally и синхронизацию сверить с байткодом. Не менять алгоритмы ради того,
чтобы компилятор перестал ругаться. Для каждого исправления хранить основание.

Зафиксировать JDK, компилятор с поддержкой требуемого старого target,
MIDP 2.0/CLDC 1.1 API jars, CLDC preverifier и их контрольные суммы.
Не компилировать телефонный код против Java SE вместо CLDC. Современный JDK
сам по себе не гарантирует выпуск совместимого bytecode 45.3 и StackMap.

Цепочка: Java → class-файлы с проверенным target → CLDC preverification →
JAR с профильными ресурсами → JAD → запуск. До реализации этой цепочки
`j2me/build.sh` остаётся только упаковщиком готовых классов.

Выход: чистая сборка из восстановленного `src/`, независимая от исходных
`.class`; оба профиля проходят базовые функциональные проверки, а любые
поведенческие отличия от 0.3.2 объяснены и проверены.

### Этап 2 — восстановить контейнер данных оригинала (P0)

От файловых обёрток двигаться к реальным вызывающим загрузчикам. Найти индекс,
границы записей, сжатие, палитры и связи сцен/объектов. Начать с одной записи
фона и одной анимации, сравнить полученные пиксели с уже доступным JAR.
Не считать всё содержимое после PE одним известным архивом без разбора.

Сохранить desktop-экстрактор, тестовые fixtures, таблицу источников и отчёт
неизвестных записей. Тестировать повреждённые/обрезанные данные и переполнения.
Не полагаться на неограниченное распаковывание недоверенного размера.

Выход: извлечение сцены 02 с происхождением каждого ресурса, затем полный
реестр записей оригинала. Повторный запуск даёт те же пиксели/данные; неизвестные
записи отражены в отчёте, а не потеряны.

### Этап 3 — координаты и актёры сцены 02 (P0)

Выполнить раздел 6. Разделить курсор, активного героя и координаты других актёров.
Реализовать отражение, pivot, движение и переключение клипа, если необходимость
подтверждена исходными данными. Сохранить отладочную визуализацию bounds/pivot.
Не подменять анимацию движения перемещением одного курсора.

Выход: все 15 замечаний о размещении и 7 замечаний о реакциях закрыты
проверяемыми эталонами на двух профилях; ID 106 не возвращается в поставку.

### Этап 4 — законченный игровой фрагмент сцены 02 (P0)

Составить таблицу доступных действий оригинала с предусловиями, исполнителем,
переходами и эффектами. Выбрать один подтверждённый пазл и реализовать полную
цепочку: осмотр → действие/неправильная попытка → правильное действие →
изменение предмета/флага → реакция/анимация → доступный игровой переход.
Конкретное решение пазла не выдумывается до проверки оригинала.

Заполнить реальные hotspots, добавить UI выбора персонажа и предмета,
ожидания событий и необходимые команды VM/адаптера. Развести подсказку,
отказ и успешное действие. Исключить продвижение через служебные 7/9 в игровом
режиме. Проверить повторный вход в сцену и отсутствие повторной выдачи предмета.

Выход: фрагмент проходится с исходного состояния без debug-команд; неправильный
путь не изменяет недопустимые флаги, правильный приводит к ожидаемому результату.

### Этап 5 — сохранения и восстановление (P0 до расширения)

Существующие 299 байт не описывают позиции героев, их задачи, выбранные предметы
и состояние диалогов. Ввести новую версию save с длиной, версией, checksum,
scene membership validation и данными, достаточными для восстановления мира.
Сохранять устойчивое логическое состояние; поток, открытый InputStream и ссылки
на объекты в save не сериализуются. Выбрать и документировать сохранение
во время анимации: безопасная контрольная точка либо полное восстановление задачи.

Мигрировать старые saves явно либо показать понятный отказ. Учесть прерывание
записи RMS, потерю/невалидность записи 1, заполненное хранилище и аварийный выход.
Сначала подготовить новую запись и проверить её, затем переключать активную
версию; неподтверждённую атомарность операций RMS не предполагать.

Выход: загрузка воспроизводит игровой результат, а не только сцену/курсор;
повреждённое сохранение не уничтожает последнюю пригодную запись.

### Этап 6 — остальные сцены и полный граф прохождения (P1)

Извлечь реальный список локаций и граф переходов. Для каждой сцены вести
чеклист: изображения/палитры, объекты, персонажи, взаимодействия, события,
звук/текст, входные и выходные состояния, save/load и предельная память.
Переносить небольшими законченными группами, не все фоны прежде всей логики.
Канализацию (шестую локацию) не переносить: утверждён маршрут улица → гостиница.

Построить сценарий прохождения от начала до финала и проверять достижимость,
тупиковые состояния и повторный вход. Не оценивать готовность процентом
картинок или количеством просмотренных анимаций.

Выход: полный маршрут игры проходится, исходы всех обязательных пазлов
сопоставлены с оригиналом; список известных отклонений явный.

### Этап 7 — звук, текст и видеопоследовательности (P1)

Начато для первых двух локаций в [0.7.0](AUDIO_0.7.0.md), расширено до пяти
в [0.11.0](FIFTH_LOCATION_0.11.0.md), затем до гостиницы в
[0.12.0](HOTEL_0.12.0.md): 251 PCM/WAV, восемь MIDI, сценарные события,
pause/resume и закрытие проигрывателей. Звук гостиницы проверен настольными
тестами; проверка на телефоне предстоит. Последующие локации и видео
ещё требуют исследования.

Сначала инвентаризация оригинала и событий вызова. Определить, что реально
воспроизводится через MIDI/MCI и где лежат данные; наличие API не определяет
формат всех ресурсов. Подобрать MMAPI-совместимые форматы для выбранных
устройств и ограничения числа/размера Players. Отсутствующий кодек должен
давать контролируемый режим без звука, не зависание логики.

Проверить кириллицу и перевод строк на маленьком экране. Если видеовставки
есть, предложить проверенный вариант последовательности кадров/картинок
с сохранением смысловых событий и согласовать обязательные отличия.

Выход: обязательные события имеют звук/текст/визуализацию либо документированное
согласованное исключение; pause/resume и закрытие Players проверены.

### Этап 8 — оптимизация, устройства и выпуск (P1)

Измерить heap и время кадра, а не выводить их из размеров ZIP. Устранить
пиковые выделения при смене сцены, скрытом MIDlet и повторе анимаций. При
необходимости реализовать профильные анимационные ресурсы: сейчас оба профиля
используют одинаковые ANM1 в координатах мира. Не делать уменьшение до
установления правильных pivot и зеркалирования.

Выход: выбранные устройства устанавливают JAR по JAD, игра проходит целиком,
длительное использование не даёт роста памяти, сборка воспроизводится
в чистом окружении и снабжена checksum, changelog и матрицей совместимости.

## 9. Ограничения памяти и производительности

В профиле 128x128 фон сцены 02 имеет растр 320×208, но мир 640×417;
в 240x320 растр и мир — 640×417. Фон 00 — соответственно 320×240 и 640×480.
Панели `.bar` и ANM1 одинаковы в двух профилях.

Для сцены 02 только массивы индексированных пикселей фона занимают
66560 / 266880 байт, панель — 40320 байт. Сумма максимальных кадров трёх
активных клипов 60/64/95 — 54622 байта. Отдельно нужны палитры, int-строки
рендеринга, streams, объекты, UI, поток, RMS и служебные буферы VM/телефона.
Это оценка из формата и кода, не измерение полного heap.

Крупнейший ANM1 на диске — `02-73.anm`, 1679089 несжатых байт;
максимальный индексированный кадр среди всех клипов — 49588 байт (`02-52.anm`).
Движок читает кадры потоково, поэтому размер файла не равен обязательному
одновременному выделению heap. Но ZIP-реализация телефона тоже может
буферизовать чтение: это необходимо измерить на целевой платформе.

Предлагаемые контрольные бюджеты задаются **после выбора устройств**:
максимальные JAR/JAD, доступный heap, max frame, время загрузки сцены,
целевой FPS и задержка ввода. Разрешение 128x128 само по себе не означает,
что телефон примет JAR 1.2 МБ. Не обещать поддержку «всех J2ME-телефонов».

Текущий поток спит 40 мс и ограничивает догоняющее время в актёрах; это
не измеренный FPS 25 и не доказательство правильной синхронизации сценариев.
Завершение действий связывать с игровыми событиями/таймлайном, а не случайной
длительностью кадра на конкретном телефоне.
