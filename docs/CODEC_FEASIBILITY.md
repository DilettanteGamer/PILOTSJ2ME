# Декодеры и CLDC 1.1: проверка возможности переноса

Этот анализ дополняет замеры размеров форматов. Маленький файл не означает маленький декодер и не гарантирует воспроизведение на телефоне. Принятые ориентиры — Opus VBR 8 кбит/с при 12 кГц и LZMA со словарём 256 КиБ. Игровой runtime и JAR в рамках этой проверки не изменялись.

[Машинный протокол](../j2me/analysis/codec-feasibility-audit.json) содержит версии исходников, контрольные суммы, команды компиляции, результаты и параметры прототипов. Исходники библиотек скачивались в `/tmp`; в игру они ещё не включены.

## LZMA1: реальное ядро собирается для CLDC

Проверено ядро [jponge/lzma-java](https://github.com/jponge/lzma-java/tree/763aeed49d92ca607c5c1e09fce7af611d59f2aa), основанное на SDK Игоря Павлова:

- `lzma/sdk/lzma/Decoder.java`, `Base.java`;
- `lzma/sdk/lz/OutWindow.java`;
- `lzma/sdk/rangecoder/Decoder.java`, `BitTreeDecoder.java`.

Эти **5 исходных файлов, 795 строк** без изменения собраны ECJ 4.6.1 с `-1.3 -target 1.1` против настоящего `cldcapi11-2.0.4.jar`, затем прошли `ProGuard -microedition` preverification. Это не компиляция против настольной Java под видом CLDC.

Получились **8 классов, 15 143 байта несжатых классов, 8 143 байта их ZIP-данных**. Целый отдельный проверочный JAR — 9 337 байт. В эти цифры не включены новый игровой контейнер, индекс, адаптер и лицензия.

В 10 тестах (5 разных ресурсов принятой версии — крупные анимации, фон и WAV; каждый со словарями 64/256 КиБ) восстановлено **11 373 260 байт**, побайтное сравнение успешно во всех случаях. Суммарное время вызовов декодирования на настольной Java 21 — 353 мс; оно не показывает скорость KVM на телефоне и не включает весь игровой путь загрузки.

Интерфейс ядра:

```
boolean setDecoderProperties(byte[] properties)
boolean code(InputStream input, OutputStream output, long unpackedSize)
```

Это push-декодер: он пишет результат в `OutputStream`. Для независимых небольших блоков это удобный интерфейс. Обёртки `lzma.streams.*` и `org.cservenak.streams.*` из того же репозитория не проверены для CLDC и не входят в прототип; их не следует автоматически переносить вместе с ядром.

### Фактическое состояние в памяти

При стандартных свойствах `lc=3, lp=0, pb=2` после настройки декодера отражением посчитан payload всех примитивных массивов:

| Словарь | Payload примитивных массивов | Объекты |
|---|---:|---:|
| 64 КиБ | 80 748 Б | 47 массивов и 37 прочих объектов |
| 256 КиБ | 277 356 Б | 47 массивов и 37 прочих объектов |

То есть выбранный словарь 262 144 байта требует ещё как минимум **15 212 байт таблиц**. В таблицу не входят заголовки/выравнивание объектов, ссылки, входные и выходные буферы, кадры, кэш, VM и аудиоплееры. Это нижняя оценка памяти состояния, не полный peak heap.

Практическая архитектура: один переиспользуемый графический декодер, независимые блоки с известными длинами, ограниченный выходной буфер и отдельный индекс. Загрузка всех 121 МБ несжатого банка в RAM не требуется. Для файла LZMA-Alone ядру передаются пять байт свойств; восьмибайтовая длина из заголовка обрабатывается контейнером. В игровом индексе лучше хранить достоверную ограниченную длину блока.

**Проверен LZMA1, не LZMA2 и не контейнер XZ.** Близкий размер LZMA2 не означает, что нынешний проверенный декодер его прочитает. В данном исследованном форке действует Apache License 2.0; исходный SDK Павлова обозначен как public domain, но это не отменяет лицензию конкретного форка.

## Opus: кандидат для переноса, но готовый Concentus JAR не CLDC

Проверены исходники [lostromb/concentus](https://github.com/lostromb/concentus/tree/3885c4e46513ef0fc81fca100189e54f1714c6ca), Java-реализация. Лицензия — BSD-подобные условия из [LICENSE](https://github.com/lostromb/concentus/blob/3885c4e46513ef0fc81fca100189e54f1714c6ca/LICENSE).

Все исходники Concentus успешно компилируются для настольной Java. После удаления encoder-only части ProGuard, без оптимизации и обфускации, замкнутый набор для `OpusDecoder(int,int)`, `decode(...short[]...)`, `resetState()` содержит **69 классов, 259 145 байт raw / 143 397 байт ZIP**. Это ориентир стоимости декодера в JAR; это ещё не размер готового CLDC-порта.

Компиляция полного исходного пакета против CLDC показывает ошибки отсутствующих API и языка. Однако нельзя приписывать декодеру все зависимости encoder-части: после анализа constant pool уменьшенного декодера **в нём нет вызовов `Math.log/exp/pow` или `List/ArrayList`**. Выбранный путь декодирования целочисленный, с fixed-point DSP.

Конкретные препятствия найденного decoder-only набора:

- `enum`, `java.lang.Enum`, сгенерированные таблицы `switch`;
- `java.util.Arrays.fill`;
- `AssertionError`;
- `StringBuilder`, появившийся при компиляции javac 8 (после переноса синтаксиса ECJ с целью 1.1 может генерировать `StringBuffer`);
- синтетические ссылки `NoSuchFieldError` от enum-switch.

Нужны замена enum-представления, небольшие локальные array helpers, перенос проверок и удаление encoder-only методов из общих исходных файлов. Простое помещение настольного JAR в приложение не решает эти проблемы. Переписывание алгоритма DSP с нуля не выглядит необходимым, но успешной CLDC-компиляции и функциональных тестов Opus-порта здесь пока нет.

### Уточнение: ограниченный SILK-NB путь

После анализа пакетов принятого профиля появилась возможность исключить неиспользуемые ветви. Но **TOC SILK-NB сам по себе не разрешает удалить CELT**: внутри SILK-пакета может находиться CELT redundancy 0–8 кГц. Исходный `OpusDecoder` проверяет это после декодирования SILK по условию `ec.tell()+17 <= 8*payloadBytes` и при необходимости запускает CELT.

Создан [отдельный настольный прототип](../j2me/analysis/codec-prototypes/SilkNbOnlyProbe.java), принимающий только `TOC=0x08` (моно, SILK-NB, 20 мс, один кадр), выдающий PCM 12 кГц и отклоняющий пакеты при выполнении условия возможной CELT redundancy. В нём нет PLC/FEC, переходов режимов и ненулевого decoder gain; это ограниченный декодер заранее проверенного банка, а не универсальный Opus.

Сначала проверены 2 893 пакета трёх образцов, затем **весь принятый банк: 327 клипов, 29 087 пакетов**. Все пакеты прошли дополнительную проверку отсутствия CELT redundancy, а PCM **побайтно совпал с полным Concentus** при сбросе обоих декодеров между клипами. Выдано 6 980 880 отсчётов до применения Ogg pre-skip/окончательной обрезки. SHA-256 полученного little-endian PCM — `f3d30baf91a5fa35752d03fa377a6ad991ed1be19b53e79b541344079d366241`. Это сравнение с Concentus, не доказательство идентичности PCM libopus или оригинальному WAV. Настольный проход обоими декодерами занял 2,279 с; это не замер скорости KVM. После ProGuard shrinking ограниченный путь содержит **38 классов, 109 567 байт raw / 58 562 байта ZIP**, без классов CELT/MDCT/FFT — примерно на 85 КБ ZIP меньше полного decoder-only набора. Это ещё не CLDC-порт. [Переносимый настольный тест](../j2me/analysis/codec-prototypes/TestSilkNbCorpus.java) принимает каталог независимых OPK1-файлов и сравнивает каждый пакет обоими декодерами.

Условие будущего применения: зафиксировать параметры кодирования, проверять каждый пакет всего банка, сохранять длины/pre-skip/gain и отклонять неподдерживаемый профиль при упаковке и чтении. В проверенном банке CELT redundancy не обнаружена, поэтому универсальный CELT/HYBRID для этого фиксированного набора не требуется. Это свойство нужно повторно проверять после любого изменения кодирования или добавления звука. В constant pool ограниченного набора из отсутствующих CLDC API остались только `java.util.Arrays.fill` для byte/int/short и конструктор `AssertionError`; enum, `StringBuilder` и CELT там уже отсутствуют. Исходные общие helper-файлы могут содержать неиспользуемые методы с другими зависимостями — при переносе их нужно исключить. Дополнительная CLDC-компиляция этого ограниченного набора пока не выполнялась.

### Контейнер и воспроизведение

`OpusDecoder` принимает отдельные Opus-пакеты, а не Ogg. Для игры потребуется демультиплексор Ogg или более простой собственный контейнер: длины пакетов, число отсчётов, `pre-skip`, окончательная длина и формат. Удаление повторяющихся комментариев и заголовков Ogg может уменьшить размер коротких клипов; при этом сведения для точной обрезки начала/конца нельзя терять.

Opus допускает декодирование с частотами **8/12/16/24/48 кГц**, но не 11 025 Гц. При 12 кГц моно 16 бит выход одного 20-мс кадра — всего **480 байт PCM**. Это размер одного выходного кадра, не всей памяти декодера.

Нативная поддержка `audio/opus`/Ogg не следует из MIDP 2.0. Возможный программный путь — выдача декодированного PCM в WAV-поток для уже используемого MMAPI. При этом **WAV 12 кГц тоже требует проверки**: работа прежнего WAV 11 025 Гц / 8 бит не гарантирует поддержку другой частоты/разрядности. Альтернатива — выход 8/16 кГц при поддержке устройства либо собственная передискретизация к поддерживаемой частоте.

Требуется сохранить исходную длительность по индексу, паузу/продолжение, повтор, приоритеты и одновременную работу MIDI с эффектами. MMAPI может читать или кэшировать поток иначе на разных устройствах. Производительность фиксированной реализации на ПК не доказывает воспроизведение трёх программно декодируемых эффектов одновременно на KVM.

## Speex: заметно меньше ядро, другой профиль затрат

Проверена копия JSpeex в [KnIfER/mdict-java](https://github.com/KnIfER/mdict-java/tree/c3bc4e4fd71fc507e5b56b99394d1a5d1f941a2d/src/main/java/org/xiph/speex). Это перенос JSpeex/Wimba/Xiph с BSD-вариантом лицензии в заголовках исходников.

Набор декодера для публичного API `SpeexDecoder` после desktop-компиляции и ProGuard shrinking: **23 класса, 95 009 байт raw / 49 345 байт ZIP**, без оптимизации и обфускации. Это меньше исследованного Concentus decoder-only набора примерно на 94 КБ ZIP, но не означает автоматически меньший размер всей звуковой подсистемы: сам звук в Speex может быть больше или хуже при равном битрейте.

Настоящая CLDC-компиляция ядра с source/target 1.3/1.1 без изменений дала 33 ошибки. В отдельной временной копии заменён `StreamCorruptedException` на `IOException`; осталось 10 ошибок — недоступные в CLDC вызовы `Math.exp`, `Math.log`, `Math.random`. Их необходимо корректно заменить или исключить неиспользуемые методы. По этому набору препятствий JSpeex проще в переносе, но он использует floating-point DSP. CLDC **1.1** поддерживает `float`/`double`; скорость такой арифметики на конкретной KVM остаётся отдельным вопросом.

У существующей обёртки `SpeexDecoder` имеются два буфера на две секунды звука: суммарно **96 000 байт при 8 кГц**, **192 000 байт при 16 кГц**, ещё без состояния самого декодера. Игровая версия должна декодировать ограниченное число кадров на пакет и использовать маленькие переиспользуемые буферы. Текущая обёртка не является разумным шаблоном бюджета heap.

## Другие форматы

| Формат | Доступные Java-исходники | Что мешает считать готовым решением CLDC |
|---|---|---|
| MP3 | [JLayer 1.0.1](https://github.com/umjammer/jlayer/tree/b2ed8f05af611b7da79e1f3299d7e4a7168f0180), LGPL 2.1 | Классический Java-декодер, но `BufferedInputStream`/`PushbackInputStream`, вспомогательные serial/reflection и PCM-output требуют отбора ядра и порта. Современный HEAD использует ещё более новые API. Нативный MP3 на конкретном телефоне может быть выгоднее любого Java-декодера, но это не универсальная гарантия MIDP. |
| Vorbis | [JOrbis/Jogg](https://github.com/ymnk/jorbis/tree/28592f3dde5134871165470e7390d66ed5f1dce5), LGPL 2.1 | Есть чистый Java-код, но floating-point transforms, кодовые книги и состояние зависят от потока. Нужно переносить ядро и контейнер, измерять heap/CPU; готовая совместимость CLDC не проверена. |
| Zstandard | [airlift/aircompressor](https://github.com/airlift/aircompressor), Apache 2.0; также zstd-jni | `zstd-jni` требует нативную библиотеку/JNI, чего обычный MIDlet не может добавить. Aircompressor — Java-альтернатива с API/доступом к памяти современных JVM; не drop-in CLDC. Сам формат не исключён, но стоимость порта пока выше доказанного LZMA1. |
| Brotli | [google/brotli Java decoder](https://github.com/google/brotli/tree/2e2bcf17ae7115d84ef6588d9a3651cc987d73e7/java/org/brotli/dec), MIT | Чистая Java-реализация есть. Текущая версия использует `java.nio.ByteBuffer` и другие отсутствующие API. Встроенный словарь выделяет ещё **122 784 байта** (`allocateDirect`), помимо ring buffer и таблиц. Требуется порт; смысл есть только при достаточном выигрыше размера. |
| Bzip2 | [Apache Ant `CBZip2InputStream`](https://github.com/apache/ant/tree/master/src/main/org/apache/tools/bzip2), Apache 2.0 | Есть старый чисто Java-декодер, но блоки 100–900 КБ и массивы обратного BWT заметно дороже самого блока: byte+int таблицы могут составлять около 5× размера блока до прочих таблиц. Для малой KVM память — существенный недостаток. Конкретный CLDC-порт здесь не собран. |
| DEFLATE | Встроенный ZIP-загрузчик JAR; [JZlib](https://github.com/ymnk/jzlib/tree/a21be20213d66eff15904d925e9b721956a01ef7), BSD | Для независимо **JAR-DEFLATED** ресурсов Java-декодер не нужен: `getResourceAsStream` уже отдаёт распакованные байты. Для внутреннего zlib-потока в STORED-ресурсе потребуется свой Inflater; CLDC не содержит `java.util.zip`. Эти два случая нельзя путать. |

Наличие исходников и указанная лицензия не означает, что лицензия/декодер уже включены в игру. При выборе библиотеки нужно сохранить условия именно используемой версии.

## Нативные возможности MIDP и PNG

Проверять аудиоформаты следует через `Manager.getSupportedContentTypes(null)`, затем реальное `createPlayer`/`realize`/`prefetch` на коротком тестовом клипе. Одного MIME-списка недостаточно для проверки частоты, буферизации и одновременного воспроизведения. [API Manager](https://docs.oracle.com/javame/config/cldc/ref-impl/midp2.0/jsr118/javax/microedition/media/Manager.html).

Для графики PNG относится к обязательному набору `Image`, а JPEG/WebP/AVIF нельзя считать универсально поддержанными. Возможность Android-эмулятора прочитать формат не доказывает способность обычного MIDP-телефона. [API Image](https://docs.oracle.com/javame/config/cldc/ref-impl/midp2.0/jsr118/javax/microedition/lcdui/Image.html). Эти Oracle-страницы не удалось загрузить из текущей среды; это ссылки на API, а не дополнительные замеры реализации.

## Практический вывод

**LZMA1 256 КиБ** — самый подтверждённый новый графический декодер: есть маленькое ядро, настоящая CLDC-компиляция, preverification и точное восстановление реальных ресурсов. Для него следует тестировать самостоятельные блоки и один общий графический рабочий буфер.

**Opus** остаётся приоритетным кандидатом по размеру звука, если принята его слышимая разница. Перенос Java-декодера выглядит технически возможным; его стоимость в JAR, PCM-выход, peak heap и скорость ещё требуют прототипа на устройстве.

**Speex** полезен как реальный альтернативный кандидат: значительно меньше измеренное Java-ядро и меньше языковых препятствий, но floating-point и соотношение качества/размера нужно оценивать вместе с аудиоматрицей. **Нативный MP3/AMR**, если поддержан целевым телефоном и приемлем по качеству, может выиграть по CPU и отсутствию собственного декодера.

Поддержка нового формата считается завершённой после декодирования всех клипов, контроля длительности и границ, сохранения приоритетов/музыки/паузы и проверки на целевой KVM. Сейчас полностью доказана совместимость ядра LZMA1 с API/bytecode CLDC; для аудиокодеков это ещё исследование пути переноса.
