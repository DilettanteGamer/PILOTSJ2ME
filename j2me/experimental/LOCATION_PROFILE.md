# Сравнительный профиль локаций: Nokia C1-02

Проверена экспериментальная 0.27.17. Это **настольный стенд с тестовыми реализациями MIDP**, а не эмулятор прошивки Nokia. Данные помогают выбрать тяжёлые сценарии для телефона; они не предсказывают его FPS.

## Параметры и воспроизведение

* Экран 128×160; действующие лимиты игры: банки 128 КиБ, сырые кадры 192 КиБ, общий растровый кэш 65536 пикселей, сжатый звук 32 КиБ, метаданные анимации 32 КиБ.
* На телефоне наблюдается Java heap 2048 КиБ. На стенде heap 32 МиБ из-за расходов JVM/AWT. Ограничение host heap до 2 МиБ не является корректной эмуляцией телефона. Пики кэшей в отчёте — выборочные замеры после кадров, не полный расход RAM или нативной памяти.
* Два сценария на сцену: неподвижный курсор и равномерный проход камеры по горизонтали через Viewport. Обработку кнопок/взаимодействия с предметами этот проход не проверяет. HUD включён как в поставляемой версии.
* 400 обновлений по 100 мс и полных отрисовок: 40 секунд логического игрового времени. При автоматическом переходе проба заканчивается; вход в гостиницу длится 216 шагов. Для сравнения используются также показатели на шаг.
* По два повтора каждого сценария в отдельных JVM: всего 64 прогона. После общего запуска MIDlet очищаются кэши графики и метаданных. Кэши ОС/ZIP не контролируются. Начальная общая загрузка MIDlet не включена во время входа в локацию.
* Основной обзор использует JIT. Отдельные контрольные прогоны `-Xint` отключают JIT, но не воспроизводят скорость ARM/KVM. В обоих режимах JVM видит один процессор и использует Serial GC. Время включает настольные реализации Graphics/Image, поэтому основной критерий — объём работы, а не настольные миллисекунды.
* Аудиовывод не активирован. Реальная подготовка MP3/MIDI, задержки MMAPI и нативная память телефона требуют проверки на устройстве.

```sh
python3 j2me/experimental/profile_locations.py
python3 j2me/experimental/profile_locations.py --scenes 4 7 13 --repeats 1 --engine interpreter
```

Пути JDK/API те же, что у существующего экспериментального сборщика. Результаты: [основной обзор](dist/location-profile-jit.json), [контроль без JIT](dist/location-profile-interpreter.json), [профиль](profiles/nokia-c1-02.json). Каждый отчёт содержит SHA-256 JAR. Частичные прогоны перезаписывают соответствующий отчёт — для повторения опубликованного обзора используйте команды выше.

## Выбор следующей проверки на телефоне

**Электрощитовая (scene 13)** — основной кандидат для проверки создания/вытеснения растров: 8961 Image за 400 шагов при неподвижном курсоре, около 22 на шаг. Следует записать вступление сначала без движения курсора, затем с движением. До оптимизации нужно установить, какие именно растры пересоздаются: фон, панель или акторы.

**Канализация (scene 7)** — основной кандидат для проверки чтений: 17,62 МБ за 400 шагов, 1696 открытий вместе с банками. Для сравнения сначала постоять на старте; затем отдельно записать движение, падение, плавание и возвращение, которых в этом обзоре нет.

**Звериный двор (scene 4)** сохраняется как контрольная сцена с уже подтверждённым на Nokia улучшением. В новом общем сценарии создаётся 1262 Image при неподвижном курсоре. Эти числа нельзя напрямую сравнивать с прежним AnimalPerformanceTest: у него четыре отрисовки на тик, частичные обновления, другой маршрут камеры и увеличение.

Это рейтинг **проверенных входов/начальных анимаций**, а не доказательство самой тяжёлой сцены полного прохождения. Далее нужны воспроизводимые сценарии действий, завершающих катсцен и отдельных головоломок. Единого балла с произвольными весами для чтений, Image и CPU нет: на телефоне эти ограничения проявляются по-разному.

Бинарные JAR/JAD не менялись; новый релиз для этого измерения не требуется.
