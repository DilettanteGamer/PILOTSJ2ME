# Экспериментальная 128×160 — 0.27.10

Повторная сборка для Nokia C1-02 после улучшения в 0.27.2 и оставшихся кратковременных просадок при нескольких одновременных анимациях. Пользователь отметил, что движение курсора уменьшает просадки. Вся игра в одном JAR размером около 12,84 МБ (12,25 МиБ). Графика, MIDI и механики сохранены. Звук теперь MP3 для MMAPI телефона; программные Opus и LZMA в эту сборку не включены.

## Состояние REALIZED на Nokia: 0.27.10

Запись VID_20261027_084708_906 с 0.27.9 подтверждает события шагов K31/W31: C растёт, H/X остаются нулевыми, S показывает 200 (REALIZED), Z4 — закрытие при очередной замене. Плеер не проходил условие повторного использования, которое принимало только PREFETCHED (300). Это объясняет отсутствие повторных запусков на показанном маршруте. Состояние фиксируется перед закрытием; запись не позволяет установить, на каком внутреннем этапе драйвер снимает предзагрузку.

В 0.27.10 завершённый плеер шагов может сохраняться и в REALIZED. При повторном событии в этом состоянии вызывается prefetch(), затем перемотка в ноль и start(). Для PREFETCHED путь прежний, без дополнительного prefetch. Создание плеера, открытие потока и realize повторять не нужно. Возможная стоимость нативного prefetch остаётся, поэтому выигрыш по FPS/задержке требует проверки телефона.

Один сохранённый завершённый плеер, таймаут 1,5 секунды, порог 128 КиБ свободного Java heap, три слота эффектов, приоритет речи и обработка ошибок сохранены. При отказе prefetch/перемотки/старта работает прежний путь создания. Неподдерживаемые состояния вне REALIZED/PREFETCHED закрываются. Графика, MP3, MIDI, скриптовые события и управление прежние.

В последней строке `B` теперь считает успешные повторные prefetch из REALIZED с запуска приложения. Вместе с накопительными `H` и `X` он покажет, работает ли новый путь на C1-02. На экране B ограничен 99. Z3 теперь означает состояние вне REALIZED/PREFETCHED. Остальные значения ниже сохраняют смысл. Настольный тест проверяет по 12 повторов из обоих состояний без новых плееров и возврат к созданию при отказе повторного prefetch. Нативная скорость и память телефона этим тестом не измеряются. Размер JAR — 12 843 433 байта (+92 байта к 0.27.9).

## Диагностика MMAPI 0.27.9

В записях VID_20261027_082832_289 и VID_20261027_082834_653 с 0.27.8 на отсчётах раз в секунду H+ остаётся нулём. Umax достигает 997 мс, Pmax — 701 мс (максимум включает первоначальную отрисовку), Lmax — 522 мс, AUmax — 555 мс, N — 22 КиБ. Это не подтверждает выигрыш от сохранения плеера; прежняя панель не показывала, какие именно события запускались, было ли завершение в PREFETCHED, либо почему плеер освобождался.

0.27.9 сохраняет графику, звук и поведение плееров 0.27.8 и добавляет наблюдения. По умолчанию показан вариант подробной панели, в котором последние две строки посвящены MMAPI. Дополнительного буфера, потока или вызовов GC нет. Левой клавишей доступны все прежние метрики: аудиодиагностика → обычная подробная панель → краткая → выключено.

* `K` — последний обработанный звуковой cue, `W` — последний cue шагов (у входа в зоопарк это 31; -1 означает, что шагов ещё не было).
* `C` — число созданий плеера шагов, `H` — успешные повторные запуски, `X` — отказы перемотки/повторного запуска. Счётчики накопительные с запуска приложения, чтобы не пропустить короткое событие между показаниями.
* `S` — состояние завершённого/освобождаемого плеера шагов: 300 = PREFETCHED, 200 = REALIZED, 400 = ещё STARTED при замене/уходе. -1 означает отсутствие наблюдения. Это состояние, зафиксированное перед закрытием, а не текущий статус закрытого объекта.
* `Z` — последняя причина: 0 = сохранён после завершения, 1 = таймаут, 2 = мало Java-памяти, 3 = драйвер оставил плеер вне PREFETCHED, 4 = замена другим звуком, 5 = смена режима/локации или закрытие, 6 = отказ перемотки/повторного старта, 7 = нехватка памяти при запуске, 8 = лишний завершённый плеер. Непосредственная причина заменяет предыдущее наблюдение.

Для проверки нужен непрерывный проход персонажа по свободному месту локации, затем такой же проход обратно. Взаимодействия с окошком/бочкой можно записать отдельно: они запускают другие звуки. По `W/C/H/X/S/Z` можно будет отделить отсутствие повторных шагов от поведения MMAPI. Ускорение этой диагностической версии не заявляется. Размер JAR — 12 843 341 байт (+858 байт к 0.27.8).

## Повторное воспроизведение шагов 0.27.8

В записях VID_20261027_080735_614 и VID_20261027_080842_302 с предыдущей сборкой U достигает 936 мс, AU — 525 мс, L — 488 мс. Pmax652 мс уже виден на первоначальной отрисовке; это накопленный максимум, а не время каждого последующего кадра. В активные периоды встречается F11, в неподвижные — F1 при A0: последнее соответствует диагностической перерисовке раз в секунду. Минимум свободного heap N опускается до 46 КиБ. Из разных игровых действий нельзя вывести точный выигрыш 0.27.7.

Исходный звук шагов у входа в зоопарк длится всего 102 мс, поэтому повторная подготовка плеера может быть дороже самого звука. Ранее завершившийся плеер шагов сразу закрывался. В 0.27.8 один завершённый MMAPI-плеер шагов сохраняется внутри прежних трёх слотов эффектов максимум на 1,5 секунды и только при свободной Java-памяти от 128 КиБ. Повтор того же события перематывает его на начало и запускает без создания/realize/prefetch нового плеера. Нативное потребление памяти плеером этим порогом не измеряется; проверка на телефоне необходима.

Продолжающиеся звуки не перезапускаются ради переиспользования; их наложение сохранено. Речь и остальные эффекты закрываются по прежним правилам. При неподдерживаемой перемотке или повторном запуске используется обычное создание плеера. Переходы, выключение звука и завершение игры освобождают все плееры; приоритет речи сохранён. Если выделение памяти под новый эффект завершается OutOfMemoryError, сохранённый завершённый плеер освобождается и запуск повторяется в пределах прежних трёх попыток. Геометрия, графика, MIDI, сжатые аудиоданные и скриптовые звуковые события не менялись.

В последней строке диагностики `H+` показывает количество удачных повторных запусков готового плеера за окно измерения. `AU` включает время такого запуска, поэтому позволит сравнить повторные шаги с первым. `E` теперь может включать один временно сохранённый завершённый плеер. Максимумы сохраняются до смены локации.

Настольный MMAPI-тест проверяет 12 повторных шагов с единственным созданием плеера, перемотку в ноль, наложение активных шагов, один сохранённый завершённый плеер, таймаут, паузу, отказ перемотки/старта, приоритет речи и очистку. Это проверка жизненного цикла, не измерение скорости или нативной памяти Nokia. JAR — 12 842 483 байта, на 646 байт больше 0.27.7. Наблюдения на телефоне с 0.27.8 приведены выше.

## Масштабирование новых кадров 0.27.7

Обе записи VID_20261027_074914_106 и VID_20261027_074945_081 показывают загрузки линейных банков (`I+`), то есть новый профиль 0.27.6. На выбранных отсчётах F меняется примерно от 2 до 10,6; при входе в первую запись виден F1,0. Максимумы U доходят до 940 мс, P — 432 мс, L — 468 мс, AU — 506 мс. Минимум свободной Java-памяти N93K является историческим минимумом, не текущим остатком. Разные действия и отсутствие одинакового маршрута не позволяют вычислить точный выигрыш относительно 0.27.5.

В 0.27.7 координата исходного столбца рассчитывается один раз на столбец, затем используется для всех строк нового растрового кадра. Например, у кадра 48×64 количество делений для выбора столбцов уменьшается с 3072 до 48. Это сокращение числа операций, не обещание ускорения FPS в 64 раза: чтение банков, создание Image, звук и прочая логика остаются. Прозрачность, округление, обрезка и масштаб совпадают с предыдущим рендерером. Небольшой массив столбцов переиспользуется внутри клипа; максимальная фактическая длина соответствует ширине его видимой/кэшируемой части. Основные бюджеты кэшей прежние. Резервная отрисовка без Image-кэша сохранена.

Настольный прогон 1500 холодных растров без JIT дал 1555 мс для 0.27.6 и 1562 мс для 0.27.7: заметного ускорения на JVM не обнаружено. Новый путь сокращает арифметику KVM, но выигрыш на телефоне пока не подтверждён. Размер JAR — 12 841 837 байт (+510 байт).

Новая сборка ещё не проверена на Nokia. Проверки сравнивают итоговые пиксели при прокрутке, увеличении и частичной перерисовке, а также поведение с отключённым кэшем.

## Горячие кадры 0.27.6

Запись VID_20261027_012837_256 с 0.27.5 показывает U до 1248 мс (предыдущая запись — до 6040), P до 441 мс, L до 607 мс и AU до 753 мс. Это разные действия и условия, поэтому точный коэффициент ускорения по двум записям не вычисляем. Java heap — 2048 КиБ; N один раз опускается до 11 КиБ, хотя текущее свободное место затем существенно выше. Это наблюдение не является доказательством GC-паузы.

316 часто используемых изображений героев и сцен с окошком, вороной и бочкой хранятся как полные индексные кадры в небольших группах: максимум четыре изображения и 32 КиБ на банк. Кадр копируется из такой группы одной операцией вместо построчной сборки из тайлов. Остальные изображения сохраняют тайлы 16×16. Палитры, прозрачность, геометрия и тайминги исходные.

Кэш банков сохраняет предел 128 КиБ и получает четыре слота вместо двух — для нескольких меньших групп одновременно. Остальные бюджеты прежние. Одинаковые по размеру массивы кэша кадров переиспользуются при вытеснении. Общий размер JAR — около 12,84 МБ.

В настольных прогонах время всей трассы оставалось близким: 105–120 мс с JIT, 277–288 мс без JIT; подтверждённого выигрыша FPS телефона эти числа не дают. Цель проверки на Nokia — уменьшение задержек на новых кадрах и при нескольких анимациях, где стоимость операций KVM отличается от настольной JVM.

Все 20 916 кадров, 6668 произвольных переходов по клипам, итоговые пиксели отрисовки, первая/вторая локации, сохранения и отдельные головоломки прошли проверки. Звук, MIDI и фоны проверены побайтно. Счётчик I+ показывает чтения линейных групп, B+ — тайловых; их сумма характеризует количество чтений данных графики за окно. На физическом C1-02 версия 0.27.6 ещё не проверена.

## Обновление сцен 0.27.5

Запись VID_20261027_010454_044 версии 0.27.4 локализовала основные задержки в обновлении: около 44-й секунды U352/6040 при P20/333, L131/285, D2/7 и AU0/0. По M Java heap телефона — 2048 КиБ; позднее N опускается до 107 КиБ. Паузы GC возможны, но счётчики не доказывают их причину. В этой записи подготовка звуковых эффектов не выполнялась.

Исправлены три источника повторной работы:

* ANM6 теперь позволяет устанавливать нужный кадр по его дескриптору. При восстановлении состояния больше не распаковываются все предыдущие изображения, которые не будут показаны. Обычное проигрывание через advance и исполнение скриптов/аудиособытий сохранены.
* При возврате к началу той же анимации адаптеры переиспользуют AnimationClip и его буферы. Это относится к ходьбе и циклам объектов в разных локациях; ANM1/ANM3 сохраняют прежний последовательный резервный путь.
* Пересборка первой локации сохраняет неизменившиеся неподвижные объекты и кэш фона. Объекты с другим состоянием заменяются, движущиеся клипы восстанавливаются на нужный кадр. При ошибке загрузки новые объекты закрываются, видимость сохранённых объектов восстанавливается.

На одном и том же полном тестовом прохождении первой локации: чтения кадров 1791 → 868, загрузки банков 359 → 159, открытия ресурсов 505 → 158. В отдельном сценарии восстановления 40 поздних кадров: 1022 → 80 декодированных кадров, 168 → 66 загрузок банков, итоговые пиксели совпадают. Это объём работы, а не измерение FPS телефона.

Дополнительно сверены 6668 переходов к началу/середине/концу всех 1667 клипов с исходными пикселями, а также полное прохождение первой и второй локаций, переходы и сохранения. Панель диагностики остаётся включённой. Ресурсы, музыка, звук и лимиты кэшей не изменены. На Nokia C1-02 версию 0.27.5 ещё предстоит проверить.

## Диагностика 0.27.4

Экранная панель включена сразу: FPS, частота обновлений и изменений сцены, длительность загрузки сцены, время обновления/рисования/чтения ресурсов/запуска звука, максимальная пауза между отрисовками, Java heap, загрузки банков, попадания в два кэша и очередь звука. Левая софт-клавиша: **подробно → кратко → выключено**; правая сохраняет меню. Назначения игровых кнопок сохранены.

[Все обозначения и порядок проверки](docs/DEBUG_HUD.md). Числа обновляются раз в секунду; собственная стоимость панели показана в D. Диагностика не создаёт Image или отдельный поток и не вызывает System.gc(). Переиспользуемый RGB-буфер занимает до 28 КиБ в подробном режиме, 8 КиБ в кратком. В выключенном режиме панель не рисуется и не запрашивает перерисовки.

Измерения на телефоне ещё предстоят; настольные тесты проверяют низкие FPS, максимумы, постоянство буфера, сохранение clipping/инвентаря, переключение левой клавишей и прежнее меню на правой. Ресурсы и механики 0.27.3 сохранены.

## Отрисовка и игровой поток в 0.27.3

Повторяющиеся масштабированные кадры сохраняются в общем кэше RasterCache: до 32 записей и 32 768 пикселей. Отдельный новый бюджет изображений не создаётся: все эти записи вместе с фоном и прочими растрами остаются внутри прежнего общего лимита 65 536 пикселей. Ключ учитывает идентификатор кадра, палитру, прозрачный индекс и размер на экране. Кэш очищается при смене локации; при вытеснении или нехватке памяти остаётся прежний путь отрисовки. Он не хранит отдельные ссылки на Image вне RasterCache.

Игровой Canvas обрабатывает не более 100 мс за один проход: после дорогой загрузки больше не выполняются четыре шага подряд под блокировкой без показа промежуточных результатов. Скриптовые шаги и аудиособытия не перескакиваются; при перегрузке игровое время замедляется. Нормальный шаг 100 мс сохранён. Между проходами вызывается serviceRepaints вне монитора Canvas, затем остаётся прежняя пауза 40 мс. Это даёт отрисовке возможность завершиться без движения курсора.

В настольном сценарии трёх циклических анимаций за 300 кадров создание Image сократилось с 780 до 11; после прогрева за 50 кадров — со 150 до нуля. Хеш всех отрисованных пикселей совпадает с 0.27.2, включая частичное обновление, прокрутку, масштабирование и резервный путь без кэша. Замер не является FPS телефона. Тест игрового потока проверяет одиночный шаг после задержки, обычное накопление 40+40+20 мс и вызов serviceRepaints без удержания блокировки Canvas.

## Баланс скорости и памяти

* Тайлы 16×16 остались в локальных банках до восьми соседних изображений с целью 64 КиБ. Банки сжаты ZIP внутри JAR. Кэш банков уменьшен с 256 до 128 КиБ, до четырёх слотов. Один большой кадр может потребовать отдельного банка; фактический максимум 266 240 байт, в таком случае прочие банки вытесняются.
* Кэш готовых кадров увеличен с 96 до 192 КиБ и с 12 до 32 слотов. Проверка двух прогретых циклов ходьбы подтверждает отсутствие повторной загрузки банков.
* Маленькие ANM6-описания читаются блоками и кэшируются до 32 КиБ. Это исключает многочисленные побайтовые обращения к потоку JAR при чтении кадров. Пиксели, палитры, смещения, прозрачность и тайминги совпадают с исходником.
* P8/bar/MIDI возвращены к обычному JAR-DEFLATE. Это немного увеличивает файл, зато исключает Java-LZMA и его словарь 256 КиБ. Музыкальные MIDI и фоны восстанавливаются побайтно.
* Исходные WAV перекодированы напрямую в моно MP3, 16 кбит/с, 11025 Гц. Промежуточный Opus не используется. MMAPI получает MIME audio/mpeg; все 327 уникальных звуков / 570 ссылок сохранены. Индекс звуков читается блоками, без отдельных файлов-алиасов. До 32 КиБ коротких сжатых звуков кэшируется, длинные реплики остаются потоковыми. Java не декодирует и не пересчитывает PCM.

Номинальный объём четырёх кэшей — 384 КиБ против прежних 416 КиБ; отдельно устранены рабочая память Java-LZMA и Opus. Это бюджет кэшей, а не размер всей Java-памяти: дополнительно нужны текущие изображения, объекты игры, VM и нативные медиабуферы. Для одиночного большого банка допускается указанное превышение. При нехватке памяти необязательный кэш кадров отключается.

Оригинальная иконка сохранена. RMS `pilots-exp-*` остаётся прежним: прогресс отделён от обычного релиза. Все локации доступны для теста.

## Проверки и границы результатов

Все 1667 анимаций / 20 916 кадров и все 52 P8/bar/MIDI-ресурса совпадают с исходником. Проверены переходы, сохранения, меню, головоломки, аудиособытия, пауза, выключение звука, освобождение плееров и отказ многоканального воспроизведения. JAR проходит CRC, JAD, classfile 45 и CLDC preverification. Отдельный тест проверяет суммарные бюджеты кэшей и отсутствие перезагрузки банков при прогретой ходьбе.

Каждый MP3 декодирован FFmpeg; его байты в JAR сверены с закреплённым корпусом. Звук сжат с потерями, как и прежний Opus: побайтового совпадения PCM не заявляем. Потоковый FFmpeg оставляет в конце некоторых клипов до 620 отсчётов заполнения (около 56 мс); обработка LAME delay/padding конкретным MMAPI может отличаться. Отчёт — [native-audio-verification.json](dist/native-audio-verification.json).

Настольный MMAPI-адаптер проверяет MIME, потоки и жизненный цикл, но не заменяет телефонный декодер. Скорость, звучание, смешивание MIDI с MP3 и задержку перед репликами необходимо проверить на C1-02. Сборка 0.27.6 проверена по двум новым записям; 0.27.7 проверена по следующим двум записям; 0.27.8 проверена по последним двум записям; 0.27.9 проверена по записи ходьбы; 0.27.10 ещё требует проверки на физическом устройстве. Итоговые замеры и SHA JAR — [verification.json](dist/verification.json).

Также сравнили обратимые варианты: XOR между кадрами увеличил графику до 23,83–28,17 МБ против 18,70 МБ простых индексных кадров до выбора исходного RLE. Предсказание соседних пикселей увеличило ZIP-банк тайлов; сортировка дала лишь около 31 КиБ экономии. Эти варианты не включены. Наибольшая ожидаемая экономия CPU здесь — передача звука в MMAPI и исключение программной распаковки P8/MIDI, а не усложнение графического кодека.

## Сборка

Инструменты: `/workspace/pilots-tools/j2me-placement`, JDK 21: `/workspace/pilots-tools/jdk-21.0.8+9`; пути заданы в build-скриптах. Нужны NumPy, Python lzma и FFmpeg для проверки звука.

```
python3 j2me/experimental/build_experiment.py
python3 j2me/experimental/run_tests.py
```

Входной корпус MP3 закреплён в input/native-mp3.zip. Сборка извлекает его без перекодирования. Для явного пересоздания корпуса из исходного релизного WAV: `python3 j2me/experimental/prepare_native_audio.py --rebuild` (нужен FFmpeg/libmp3lame), затем повторить все проверки. Скрипт сохраняет хеши исходных WAV.

`PILOTS_FAST_NATIVE=0` оставляет прежний профиль с программными LZMA/Opus; дополнительно `PILOTS_NATIVE_TILES=0` выбирает LZMA-банки тайлов. Путь выходного JAR тот же. Текущий run_tests.py предназначен для нового нативного профиля; предыдущие тесты декодера и закреплённый Opus-корпус сохранены для исследований. Подробная проверенная версия прежнего профиля — коммит 52c84f7.
