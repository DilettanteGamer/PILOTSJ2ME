# J2ME-версии и анализ

Подробный [план переноса](../docs/J2ME_PORTING_PLAN.md).

* `input/` — предоставленные пользователем JAR 0.3.2, без изменений;
  SHA-256 зафиксированы в `baselines.json`.
* `dist/` — переупакованные версии 0.3.3, JAD и отчёты: удалена только
  «31 Деталь»/ID 106 и обновлена версия. Это не новый движок.
* `analysis/decompiled/` — CFR 0.152, декомпиляция JAR 240x320 версии 0.3.2
  для изучения; классы двух профилей побайтово идентичны. Это не оригинальные
  исходники и не проверенный проект сборки. `AnimationClip.paint` восстановлен
  некорректно, а `GameCanvas.run` имеет предупреждение декомпилятора.
* `analysis/animation-catalog.json` — исходные номера меню, ресурсные ID,
  текущие координаты и замечания пользователя, а не исправленные координаты.
* `analysis/inventory.json` — проверяемая статическая опись всех четырёх JAR.

Из корня репозитория, Python 3.9+ со стандартными zipfile/zlib:

```sh
./j2me/build.sh
python3 j2me/analyze.py
```

Первый сценарий проверяет исходные SHA-256, ресурсы и каталоги, применяет
`animation-adjustments.json`, создаёт JAR/JAD и сверяет байткод с оригиналом.
Второй создаёт статическую опись, включая Java API, количество hotspot-областей
и привязки актёров. Повторная упаковка проверена на этой машине. Результаты
не подтверждают запуск на телефоне и не заменяют preverification после
будущих изменений Java-классов. Между разными zlib сжатые байты могут различаться.

В `animation-adjustments.json` списки `pending_*` и `character_relative_*`
только фиксируют требования. Координаты и динамические привязки не исправлены.
`anchors` принимает явные фиксированные координаты по ID ресурса;
механизма привязки к текущему положению персонажа этот сценарий не добавляет.
Простая замена поля `Pilots-Screen` не конвертирует профиль: растры фонов различны.
